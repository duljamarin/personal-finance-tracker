# Deploying `20260705055049_encrypt_amounts.sql`

E2E-encrypts all monetary amounts. **Ordering matters** because the frontend
flag `ENCRYPT_AMOUNTS` (src/utils/crypto/fieldMap.js) is `true`: an
encryption-enabled client will write `enc:v1:...` ciphertext into the amount
columns, which fails while those columns are still `NUMERIC`.

## Correct order
1. **Apply this migration first** (retypes the amount columns to `text`, drops
   the amount-reading RPCs/triggers/CHECK constraints, resets the E2EE
   migration cursor).
2. **Then deploy the frontend** (push to `main` → Netlify auto-deploy).

Applying the migration before the FE is safe: stale clients write plaintext
numbers into `text` columns (accepted) and read text amounts via `Number()`
(coerces fine). Deploying the FE *before* the migration is NOT safe.

## Apply command
This repo keeps migrations in `supabase_migrations/` (not the CLI default
`supabase/migrations/`), so apply manually — e.g. paste into the Supabase SQL
editor, or:

```bash
supabase db execute --file supabase_migrations/20260705055049_encrypt_amounts.sql
```

## What happens to existing data
- Existing plaintext numeric amounts are cast to text (`123.45` → `"123.45"`)
  and keep working (client coerces back to Number on read).
- The cursor reset (`UPDATE user_keys SET migration_cursor = '{}'`) makes the
  client-side E2EE migration runner re-scan every table on the next unlock for
  each encryption-enabled user, encrypting historical plaintext amounts.
  Idempotent — already-encrypted values are skipped.
- Users with encryption OFF are unaffected; amounts stay plaintext text.

## Rollback
Reversible in principle (retype `text -> numeric USING col::numeric`) ONLY if
no amounts have been encrypted yet. Once ciphertext exists, a straight cast
back to numeric will fail — you'd first disable encryption per user (the
existing decrypt-direction migration runner) to restore plaintext.
